# Стемік — навчальні версії сайту для лабораторних робіт

Окремий від CRM сайт: для кожної лабораторної — своя сторінка (`labs/lr1/`, `labs/lr2/`, …),
яка показує результат саме цієї роботи на базі даних цього етапу. Кожен наступний етап
**доповнює** попередній: SQL-файли етапів виконуються по черзі в одному навчальному проєкті
Supabase, і сторінки попередніх етапів після цього продовжують працювати.

| Сайт | Для чого | Проєкт Supabase |
|---|---|---|
| CRM (`index.html` у корені) | захист МКР1, далі — ЛР5 (форми для кінцевого користувача) | **Stemik_bd** — не чіпати |
| Навчальні версії (`labs/`) | захист ЛР1–ЛР4, далі ЛР6 | **окремий новий проєкт** |

> ⚠️ **Не виконуйте SQL етапів ЛР2 і ЛР3 у проєкті CRM (Stemik_bd).**
> Файли `lr2_01_schema.sql` і `lr3_01_create_tables.sql` починаються з
> `DROP SCHEMA stemik CASCADE` і знищать базу, з якою працює CRM.
> Безкоштовний тариф Supabase дозволяє 2 активні проєкти — другий якраз для лабораторних.

---

## Крок 1. Новий проєкт Supabase для лабораторних

supabase.com/dashboard → **New project** → назва, наприклад, `stemik-labs` → регіон той самий →
дочекатися створення.

## Крок 2. SQL етапів — по черзі, у SQL Editor нового проєкту

Кожен файл: **SQL Editor → + New query → відкрити файл у Блокноті → Ctrl+A, Ctrl+C →
вставити → Run**. Текст беріть **з файлу**, а не з чату/месенджера (вони можуть «з’їсти»
символи `||`). На вікно про RLS відповідайте **Run and enable RLS**: сайт працює через функції,
на які RLS не впливає. Попередження про «destructive operations» стосується `DROP` у скриптах —
у навчальному проєкті це нормально.

Файли лежать у `docs/db-labs/stages/lrN/db/`. Виконуйте **лише до етапу, який захищаєте**
(наприклад, для ЛР2 — блоки ЛР1 і ЛР2), але завжди починаючи з ЛР1.

| Етап | Файли — суворо в цьому порядку | Перевірка в SQL Editor |
|---|---|---|
| **ЛР1** | `lr1_01_part1.sql` … `lr1_01_part7.sql` (знеособлена копія робочої бази, 7 частин), `lr1_02_site_api.sql` | `select lab_lr1_overview();` → JSON з `"student_ids_orphan": 41` |
| **ЛР2** | `lr2_01_schema.sql`, `lr2_02_seed.sql`, `lr2_03_site_api.sql` | `select count(*) filter (where ok) from lab_lr2_constraint_tests();` → `10` |
| **ЛР3** | `lr3_01_create_tables.sql`, `lr3_02_migrate.sql`, `lr3_03_site_api.sql`, `lr3_04_alter.sql` | `select count(*) filter (where ok) from lab_lr3_demos();` → `14` |
| **ЛР4** | `lr4_01_views.sql`, `lr4_02_site_api.sql` | `select lab_lr4_overview();` → `"queries": 24` |

Що відбувається з базою:

- **ЛР1** — у схемі `public` з’являється копія робочої бази студії (16 таблиць) — об’єкт аналізу.
- **ЛР2** — у схемі `stemik` створюється спроєктована модель (18 таблиць) з тестовими даними.
- **ЛР3** — модель перестворюється з іменованими обмеженнями й заповнюється **реальними** даними з копії (`INSERT … SELECT`, 2480 рядків). Тести ЛР2 після цього так само дають 10/10.
- **ЛР4** — додаються 2 представлення і каталог із 24 запитів.

Якщо файл виконався з помилкою — почніть етап спочатку з його першого файлу
(для ЛР1 — з `lr1_01_part1.sql`: він сам видаляє попередню копію).

## Крок 3. Файли сайту на GitHub

У той самий репозиторій, де вже лежить CRM, додайте **дві теки зі збереженням структури**:

```
<репозиторій>/
├── index.html, app.js, … ← CRM (як і було)
├── labs/                 ← навчальні версії сайту
└── docs/db-labs/         ← протоколи, презентації, SQL етапів (на них посилається сайт)
```

**Add file → Upload files** → перетягнути теки `labs` і `docs` з архіву → **Commit changes**.
За раз можна завантажити до 100 файлів; якщо GitHub попросить, завантажте частинами.

## Крок 4. Налаштування `labs/`

**`labs/config.js`** — адреса й ключ **нового** проєкту (Project Settings → API Keys):

```js
window.LAB_CONFIG = {
  url: 'https://<id-нового-проєкту>.supabase.co',
  anonKey: 'eyJ…'   // anon (Legacy) або sb_publishable_… — не service_role!
};
```

Перевірте, що `<id>` в адресі збігається з ID проєкту в **Project Settings → General**
(саме через розбіжність виникала помилка «Invalid API key» у CRM).

**`labs/stages.js`** — скільки етапів показувати в меню:

```js
window.LAB_PUBLISHED = 2;   // захищаємо ЛР2 → у меню ЛР1 і ЛР2, решта сірі
```

Після кожного захисту збільшуйте число й виконуйте SQL наступного етапу.

## Крок 5. Відкрити

`https://<обліковий-запис>.github.io/<репозиторій>/labs/` — головна сторінка з етапами,
звідти — «Версія сайту», протокол, презентація й SQL кожної ЛР.
Наприклад: `https://skywalker345.github.io/stemikprg.github.io/labs/lr2/`.

Вхід на сторінки лабораторних не потрібен: функції `lab_*` повертають лише агрегати,
знеособлені рядки й демонстрації, які виконуються з відкатом і базу не змінюють.

## Що показує кожна сторінка

| Сторінка | Що на ній | Функції бази |
|---|---|---|
| `labs/lr1/` | аналіз робочої бази: таблиці, зв’язки, знайдені аномалії | `lab_lr1_overview()` |
| `labs/lr2/` | модель у СУБД: таблиці, ключі, обмеження; 10 тестів обмежень наживо | `lab_lr2_model()`, `lab_lr2_constraint_tests()` |
| `labs/lr3/` | перенесення реальних даних, перегляд таблиць, 14 демонстрацій ALTER/UPDATE/DELETE/TRUNCATE/DROP | `lab_lr3_overview()`, `lab_lr3_browse()`, `lab_lr3_demos()` |
| `labs/lr4/` | 24 запити з бізнес-задачами, виконання наживо | `lab_lr4_catalog()`, `lab_lr4_run()`, `lab_lr4_overview()` |
