# Стемік — навчальні версії сайту для лабораторних робіт

Окремий від CRM сайт: для кожної лабораторної — своя сторінка (`labs/lr1/`, `labs/lr2/`, …),
яка показує результат саме цієї роботи. Сайти різні, але можуть жити **в одному репозиторії
GitHub** і працювати з **одним проєктом Supabase** разом із CRM.

| Сайт | Для чого | Де в репозиторії |
|---|---|---|
| CRM | захист МКР1, далі — ЛР5 (форми для кінцевого користувача) | корінь: `index.html`, `app.js`, … |
| Навчальні версії | захист ЛР1–ЛР4, далі ЛР6 | `labs/` + `docs/db-labs/` |

---

## Варіант А (основний): один проєкт Supabase разом із CRM — Stemik_bd

База CRM — це вже **готовий результат ЛР3 і ЛР4**: та сама структура (18 таблиць, 86 обмежень),
ті самі 2480 рядків, ті самі представлення. Тому для цих етапів у проєкт додаються лише функції
сайту. Модель ЛР2 відрізняється від моделі CRM, тож вона створюється в **окремій схемі
`stemik_model`** — CRM її не бачить і не зачіпає.

> ⚠️ У цьому варіанті **не виконуйте** файли `lr2/db/lr2_01_schema.sql`,
> `lr3/db/lr3_01_create_tables.sql`, `lr3/db/lr3_02_migrate.sql` — вони видаляють схему
> `stemik` і зламають CRM. Беріть лише файли з таблиці нижче.

Кожен файл: **SQL Editor → + New query → відкрити файл у Блокноті → Ctrl+A, Ctrl+C → вставити → Run**.
Текст беріть **з файлу**, а не з чату/месенджера. На вікно про RLS — **Run and enable RLS**.
Виконуйте етапи по черзі, лише до того, який захищаєте, але завжди починаючи з ЛР1.

| Етап | Файли — суворо в цьому порядку | Перевірка в SQL Editor |
|---|---|---|
| **ЛР1** | `docs/db-labs/stages/lr1/db/lr1_01_part1.sql` … `lr1_01_part7.sql`, потім `lr1_02_site_api.sql` | `select lab_lr1_overview()->'anomalies'->>'student_ids_orphan';` → `41` |
| **ЛР2** | `docs/db-labs/stages/lr2/db/`**`one-project/`**`lr2_01_schema.sql`, `lr2_02_seed.sql`, `lr2_03_site_api.sql` | `select count(*) filter (where ok) from lab_lr2_constraint_tests();` → `10` |
| **ЛР3** | лише `docs/db-labs/stages/lr3/db/lr3_03_site_api.sql` | `select count(*) filter (where ok) from lab_lr3_demos();` → `14` |
| **ЛР4** | лише `docs/db-labs/stages/lr4/db/lr4_02_site_api.sql` | `select lab_lr4_overview()->>'queries';` → `24` |

Після кожного етапу перевіряйте й CRM: `select crm_ping();` має й далі показувати 52 учні.
Демонстрації ЛР2 і ЛР3 (помилки обмежень, ALTER/DELETE/TRUNCATE/DROP) виконуються з відкатом —
дані CRM вони не змінюють.

**Що з’явиться в проєкті:**

- **ЛР1** — у схемі `public` копія робочої бази студії (16 таблиць) — об’єкт аналізу ЛР1.
  У **Authentication → Users** з’являться 8 службових записів `user0X@example.test` — це
  працівники з копії, **без паролів**: увійти ними неможливо, CRM вони не заважають.
  Нові користувачі Auth створюються як і раніше.
- **ЛР2** — схема `stemik_model`: модель ЛР2 (18 таблиць) з тестовими даними.
- **ЛР3** — функції, що показують перенесення даних з копії в схему `stemik` (вона вже є — це база CRM).
- **ЛР4** — каталог 24 запитів (таблиця `stemik.lab_query`) і функції для сайту.

**Перед захистом ЛР3/ЛР4**, якщо в CRM додавали демо-учнів чи відмітки, поверніть базу CRM
до початкового стану: `crm-demo/sql/01_schema.sql`, `02_data_1…6.sql`, `03_views.sql`,
`04_crm_api.sql`, а потім **знову** `lr3_03_site_api.sql` і `lr4_02_site_api.sql`
(`01_schema.sql` перестворює схему `stemik`, а з нею й таблицю запитів ЛР4).

## Варіант Б: окремий проєкт Supabase для лабораторних

Якщо є вільний слот (безкоштовний тариф — 2 активні проєкти; непотрібний проєкт можна
поставити на паузу: Project Settings → General → Pause project), лабораторні можна тримати
окремо від CRM. Тоді в новому проєкті виконуються **повні** набори файлів етапів:

| Етап | Файли |
|---|---|
| ЛР1 | `lr1_01_part1…7.sql`, `lr1_02_site_api.sql` |
| ЛР2 | `lr2/db/lr2_01_schema.sql`, `lr2_02_seed.sql`, `lr2_03_site_api.sql` |
| ЛР3 | `lr3_01_create_tables.sql`, `lr3_02_migrate.sql`, `lr3_03_site_api.sql`, `lr3_04_alter.sql` |
| ЛР4 | `lr4_01_views.sql`, `lr4_02_site_api.sql` |

## Файли сайту на GitHub

У той самий репозиторій, де вже лежить CRM, додайте **дві теки зі збереженням структури**:

```
<репозиторій>/
├── index.html, app.js, … ← CRM (як і було)
├── labs/                 ← навчальні версії сайту
└── docs/db-labs/         ← протоколи, презентації, SQL етапів (на них посилається сайт)
```

**Add file → Upload files** → перетягнути теки `labs` і `docs` з архіву → **Commit changes**
(до 100 файлів за раз; якщо GitHub попросить — частинами).

## Налаштування `labs/`

**`labs/config.js`** — у варіанті А **ті самі** адреса й ключ, що в `config.js` CRM:

```js
window.LAB_CONFIG = {
  url: 'https://eiexcdqzwtgagwyvajqt.supabase.co',
  anonKey: 'eyJ…'   // anon (Legacy) або sb_publishable_… — не service_role!
};
```

**`labs/stages.js`** — скільки етапів показувати в меню:

```js
window.LAB_PUBLISHED = 2;   // захищаємо ЛР2 → у меню ЛР1 і ЛР2, решта сірі
```

Після кожного захисту збільшуйте число й виконуйте SQL наступного етапу.

## Відкрити

`https://<обліковий-запис>.github.io/<репозиторій>/labs/` — головна сторінка з етапами,
звідти — «Версія сайту», протокол, презентація й SQL кожної ЛР.
Наприклад: `https://skywalker345.github.io/stemikprg.github.io/labs/lr2/`.

Вхід на сторінки лабораторних не потрібен: функції `lab_*` повертають лише агрегати,
знеособлені рядки й демонстрації, які виконуються з відкатом.

## Що показує кожна сторінка

| Сторінка | Що на ній | Функції бази |
|---|---|---|
| `labs/lr1/` | аналіз робочої бази: таблиці, зв’язки, знайдені аномалії | `lab_lr1_overview()` |
| `labs/lr2/` | модель у СУБД: таблиці, ключі, обмеження; 10 тестів обмежень наживо | `lab_lr2_model()`, `lab_lr2_constraint_tests()` |
| `labs/lr3/` | перенесення реальних даних, перегляд таблиць, 14 демонстрацій ALTER/UPDATE/DELETE/TRUNCATE/DROP | `lab_lr3_overview()`, `lab_lr3_browse()`, `lab_lr3_demos()` |
| `labs/lr4/` | 24 запити з бізнес-задачами, виконання наживо | `lab_lr4_catalog()`, `lab_lr4_run()`, `lab_lr4_overview()` |
